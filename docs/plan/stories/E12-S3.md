# E12-S3 — GitHub release workflow and `v1.0.0` tag runbook

**User story.**
As a release engineer, I want a documented GitHub release workflow and `v1.0.0` tag runbook, so v1.0.0 can ship once through a controlled process before v1.1 feature work lands.

**Acceptance criteria.**
- The plan defines a tag-triggered GitHub Actions workflow that runs tests, validates GoReleaser, builds artifacts, uploads checksums, and publishes a GitHub Release.
- Required workflow permissions and secrets are listed explicitly with least privilege.
- The `v1.0.0` tag sequence is documented end-to-end: preflight checks, changelog/release notes, tag creation, push, workflow observation, artifact verification, and rollback/retry guidance.
- The story states that the actual `v1.0.0` tag operation is owned by the separate release-engineering effort, not by v1.1 planning.
- Release notes must call out v1.0 scope boundaries: local-first, Claude Code + Codex CLI, plaintext `0600`, no cloud/MCP/GUI/Gemini/encryption claims.
- Failed publish leaves enough diagnostics to retry without creating ambiguous duplicate releases.

**PRD/architecture refs.** ADR-0002 E12, Locked Decision 5; ADR-0001 Locked Decisions; PRD release gates NFR-D1/NFR-T1.

**Test plan.**
- Happy: dry-run workflow on a test tag or manual rehearsal validates tests, GoReleaser config, artifacts, and release-note template.
- Edge: missing secret/permission fails before publish; failed release can be deleted/retried according to runbook.

**No fallback writes.** N/A for planning; implementation must not tag or publish from a non-release branch.

**Complexity.** M.

**Dependencies.** E12-S1, E12-S2, E8-S2, E8-S3, E8-S6.

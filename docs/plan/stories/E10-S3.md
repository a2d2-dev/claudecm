# E10-S3 — Preset override, activation, and write-path invariants

**User story.**
As a claudecm maintainer, I want preset-created profiles to activate through the exact same switch/write path as hand-authored profiles, so provider convenience does not bypass safety guarantees.

**Acceptance criteria.**
- A preset-backed profile is stored as ordinary profile YAML and can be inspected, edited, exported, explained, and switched like any other profile.
- If `add --preset` supports an activation option or chains into `switch`, every tool-config mutation routes through `internal/commit` and `internal/writepath`.
- Preset-generated tool overlays are treated as profile intent; switch applies overlay-as-truth semantics and shows reset/default behavior in the pre-apply diff.
- Existing owned-key allowlists remain explicit. Presets may populate named provider fields admitted by ADR-0002, but do not create wildcard ownership of arbitrary provider names.
- Non-owned keys in Claude Code and Codex files remain merge-preserved during preset-backed activation.
- Preset-backed activation creates backups, honors `--dry-run`, honors `--yes`, and reports rollback/partial-failure errors identically to named `switch`.

**PRD/architecture refs.** ADR-0002 Amendments 2, Locked Decisions 3; PRD FR-4, FR-5, FR-15, FR-16, §4.7, NFR-S6; Architecture §4, §5.

**Test plan.**
- Happy: switch to a preset-backed profile → pre-apply diff shows generated owned-key changes, backups are reported, `current` confirms.
- Edge: malformed target config refuses via NFR-S1; non-owned keys survive activation; concurrent edit returns exit code 2 with backup retained.

**No fallback writes.** Preset activation never writes directly to tool files; all mutations route through `commit`/`writepath`.

**Complexity.** M.

**Dependencies.** E10-S2, E6-S2, E7-S1..E7-S5.
